00 The whole argument

A GPU is a data-moving machine
with very fast math attached.

An H100 SXM does ~989 TFLOP/s in bf16. Its memory delivers 3.35 TB/s.

If every multiply-add had to fetch both inputs from main memory, memory could keep up with less than 0.2% of the math.

WHAT MEMORY ALONE SUSTAINS
1.7 TFLOP/s

3.35 × 10¹² B/s4 B per FMA ≈ 0.84 × 10¹² FMA/s

0.17% of the 989 TFLOP/s compute ceiling.

How to read that number

This is a ratio of two published numbers, not a measurement. Two bf16 inputs are 4 bytes and one FMA is 2 FLOPs, so the memory-side ceiling is 0.84 × 10¹² × 2 ≈ 1.7 TFLOP/s. Real kernels do far better because of caches and reuse — and designing that reuse is what the rest of this deck is about.

989 TFLOP/s is the dense bf16 Tensor Core figure for H100 SXM. The PCIe part differs, and ordinary FP32 instructions have a completely different ceiling. Always compare against the path and dtype your kernel actually executes.

01 The problem

Three loops, and no clever trick

Each cell of C is one dot product: a row of A against a column of B.

Cᵢⱼ = Σₖ Aᵢₖ Bₖⱼ
definition

M·N outputs, each needing K multiply-adds. One FMA counts as 2 FLOPs.

FLOPs = 2 · M · N · K
work
# mathematically, this is all of it
for i in range(M):
  for j in range(N):
    acc = 0
    for k in range(K):
      acc += A[i][k] * B[k][j]
    C[i][j] = acc

At M=N=K=4096

2 × 4096³ ≈ 1.37 × 10¹¹ FLOPs. At an assumed 10 TFLOP/s, 13.7 ms.

A calculation, not a measurement. Real time also depends on memory, instructions, and synchronization.

The amount of arithmetic is fixed. What we get to change is the order we do it in, and the data movement it implies.

02 Layout

The same numbers, different addresses

In row-major storage, one row's values are consecutive, then the next row follows.

A = [ 1  2  3  4 ]     element idx:  0  1  2  3 | 4  5  6  7 | 8 ...
    [ 5  6  7  8 ]     value:        1  2  3  4 | 5  6  7  8 | 9 ...
    [ 9 10 11 12 ]     byte offset:  0  4  8 12 |16 20 24 28 |32 ...
    [13 14 15 16 ]
                       A[1,2] = 7  →  element 6  →  byte 24

The formula

row × width + col

Byte offset is that times the element size. The pointer does not remember the matrix shape.

Walking a row

0, 1, 2, 3 … stride 1

Neighbouring addresses. One transfer's bytes all get used.

Walking a column

0, 4, 8, 12 … stride = width

Far-apart values. Most of each transfer can be thrown away.

The question that changes on a GPU

On a CPU you usually study one thread's addresses over time. On a GPU there is a second question: which addresses do neighbouring lanes request in the same instruction? The same kernel gives a different answer when you change the block shape.

further readingDrepper's What Every Programmer Should Know About Memory §3.3.2 measures exactly this by varying working-set size and traversal order. Carry forward the method, not the 2007 cycle counts.

03 Two measurements

Latency and bandwidth are not the same

Latency

How long until one request produces its result. Nanoseconds.

Bandwidth

How many bytes can be delivered per second. GB/s.

A system can have high bandwidth and high latency. Sustaining the rate requires many requests in flight at once.

64 GB/s × 100 ns = 6,400 bytes in flight
illustrative

read aloudIf an imaginary memory answers in 100 ns and sustains 64 GB/s, roughly 6,400 bytes must be in flight at all times. One dependent four-byte request at a time will never get there.

Dependent

Read an index → use it to find the next address → read that. You cannot issue the next useful request until this one returns.

Independent

Read A[0], A[1], A[2] without waiting. The hardware can keep several requests in progress.

GPUs keep many warps resident to hide latency. That does not make an individual request finish sooner, and it does not raise the bandwidth limit.

04 The first kernel

One thread, one output cell

__global__ void naive_matmul(int M, int N, int K,
      const float* A, const float* B, float* C) {
  int col = blockIdx.x * blockDim.x + threadIdx.x;
  int row = blockIdx.y * blockDim.y + threadIdx.y;
  if (row < M && col < N) {        // edge guard
    float acc = 0.0f;
    for (int k = 0; k < K; ++k)
      acc += A[row * K + k] * B[k * N + col];
    C[row * N + col] = acc;
  }
}
dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);   // round up
naive_matmul<<<grid, block>>>(M, N, K, dA, dB, dC);

What each thread does

Not a fraction of a dot product — the entire dot product, looping over K itself.

No thread waits for another. Each reads inputs and writes a different output.

Why round up

Integer division truncates. Adding 15 before dividing by 16 rounds up to the blocks needed. If N is 17, we need two blocks across.

Some threads in the final block lie outside the matrix; the if keeps them from touching invalid elements.

This kernel is correct. It is merely slow, and the next chapter looks at why, address by address.

The chip

H100 SXM has 132 SMs, the PCIe part 114. The die holds 144; some are fused off for yield.

Inside an SM

4 sub-partitions, each with a warp scheduler, a slice of the register file, arithmetic units, and one Tensor Core.

SIMT

One issued warp instruction applies to the participating lanes, each on its own data. Divergent lanes reduce useful work per instruction.

06 The hierarchy

Fast memory is small. Big memory is slow.

This comes from physics. SRAM needs ~6 transistors per bit and must sit next to the compute. DRAM needs 1 transistor + 1 capacitor, so it is dense but slower and off-chip.

LevelWhat it isSize on H100Analogy

The rule

Copy useful chunks up the hierarchy, reuse them many times while they are up there, and avoid going back to HBM for the same data.

Not a mandatory route

An ordinary global load can be served by a cache straight into a register. It does not pass through a shared-memory array unless the kernel explicitly stages it there.

Global memory names an address space; HBM names the physical technology. A global access that hits L2 never reaches HBM — a distinction that matters once we start counting traffic.

07 Latency hiding

Occupancy is not the goal

One H100 SM can hold 2048 threads (64 warps) at once. While warp A waits hundreds of cycles for a load, the scheduler switches to another warp that is ready.

Without enough warps:        With many warps:
A: load ░░░░░░░ compute      A: load ░░░░░░░ compute
   (SM idle)                 B:   compute load ░░░░
                             C:     load ░░░░ compute
                             → more chances to issue work

Worked occupancy

1024 × 32 = 32,768 regs per block

65,536 ÷ 32,768 = 2 blocks per SM

2 × 1024 = 2048 threads = 100% occupancy.

But

Maximum occupancy ≠ maximum performance. Fast matmul kernels deliberately use many registers and lots of SMEM. That lowers occupancy but cuts memory traffic, and it wins.

The goal is not to maximize occupancy. It is to keep the machine busy.

Occupancy counts resident warps, not ready instructions or useful arithmetic. It is a resource measure, not a performance score.

08 Pitfall 1 · coalescing

The same kernel, 13× slower

Swap threadIdx.x and .y in row and col. The mathematics is identical; the addresses a warp requests in one instruction are not.

Warp walks a row of C

A[row*K + k] → all same · broadcast

B[k*N + col] → consecutive · coalesced

3171 GFLOP/s

Warp walks a column of C

A[row*K + k] → stride K = 4096 · uncoalesced

C[row*N + col] → stride N · uncoalesced

243 GFLOP/s

Move the slider: as 32 lanes read FP32 values with a stride, the number of 32-byte sectors requested changes. Stride 1 needs four sectors at 100% efficiency; stride 2 needs eight at 50%; from stride 8 on it saturates at 32 sectors and 12.5%.

Where these numbers come from

The 3171 → 243 GFLOP/s figures are reported by Gordić's case study on an H100 PCIe with 4096×4096 matrices — not measured here. The canvas computes requested sectors locally; a sector count alone does not explain a 13× gap, since cache hits and instruction behaviour also contribute.

The address diagrams assume a 32×32 block, where a warp is exactly one row. The runnable example uses 16×16 blocks, where a warp spans two rows — the same kernel, a different access pattern.

09 Pitfall 2 · arithmetic intensity

Count requests and transfers separately

For one output, a thread requests K values from A and K from B. In FP32 that is 8K input bytes for about 2K FLOPs.

2K FLOPs8K bytes = 0.25 FLOP per requested byte
source level

This is not HBM intensity

Within a warp, many threads may request the same value and share the transfer. Caches also serve repeats. A byte requested many times need not cross the HBM interface many times.

Always name the boundary

Arithmetic intensity is operations per byte across a specified boundary: HBM to chip, L2 to SM, SMEM to registers, or simply source-level requested bytes.

The naive kernel's weakness is not that it has no reuse. It is that it does not explicitly organize cooperative reuse across the output tile.

10 The ceiling

Roofline — a bound, not a prediction

achieved ≤ min( P , AI × B )
bound

P is peak throughput for the actual arithmetic path and dtype; B is bandwidth at that memory boundary.

The ridge point

With an illustrative P = 60 TFLOP/s and B = 2 TB/s, the ceilings meet at 60/2 = 30 FLOP/byte. Below it bandwidth is the lower bound; above it, compute.

Compare like with like

Do not judge an ordinary FP32 kernel against the much higher bf16 Tensor Core ceiling. That ceiling belongs to a different path.

The slider turns square tile size into AI: for FP32, AI = T/4, so 1×1 gives 0.25, 32×32 gives 8, and 128×128 gives 32 FLOP/byte. Real performance may sit well below either ceiling because of dependencies, instruction overhead, or too little parallelism.

11 Pitfall 3 · quantization

Work comes in discrete chunks

Tile quantization

If a block computes a 32×32 tile but the matrix is 4100 wide, the last column of blocks covers only 4 useful columns. The other 28 columns of threads exist, take resources, and do nothing.

Careful in a cooperating kernel

The naive kernel may exit early. In a shared-memory kernel, edge threads must still perform loads and reach barriers — guard the accesses and the store, never return before synchronization.

Wave quantization

A wave is one round of blocks that fills every SM at once.

blocks   = (4096/32)² = 16,384
per wave = 114 SMs × 2 blocks = 228
           16,384 / 228 ≈ 71.9 waves

→ 71 full waves plus a partial last one

The tail effect

115 equal blocks on 114 SMs takes two full rounds, and in the second round 113 SMs sit idle.

Size determines how much this costs: a partial final wave is negligible in a long run and can dominate a very short one. Real scheduling is not a global wave barrier, and block durations differ — this model isolates tail inefficiency.

12 Cooperation

One block, one tile

The naive kernel already gave each block a rectangle of outputs. The new idea is cooperation on the input data: load a tile together, reuse it from SMEM, and coordinate when it may be overwritten.

__shared__ float As[T][T], Bs[T][T];
float acc = 0.0f;
for (int k0 = 0; k0 < K; k0 += T) {
  As[ty][tx] = (row < M && k0+tx < K)
                 ? A[row*K + k0+tx] : 0.0f;
  Bs[ty][tx] = (k0+ty < K && col < N)
                 ? B[(k0+ty)*N + col] : 0.0f;
  __syncthreads();   // all writes done
  for (int k = 0; k < T; ++k)
    acc += As[ty][k] * Bs[k][tx];
  __syncthreads();   // all reads done
}
if (row < M && col < N) C[row*N + col] = acc;

The first barrier

Stops threads from reading SMEM before others have finished writing it.

The second barrier

Stops a fast thread from overwriting — on the next iteration — a tile a slow thread is still reading. One thread finishing does not mean all did.

Out of range becomes zero

It contributes nothing to the sum, so partial tiles stay correct. Every thread reaches both barriers; only the final store is conditional.

For a full T×T tile, each loaded value is reused T times. With T = 16, that is 16 uses per value.

13 The reuse formula

Why bigger tiles reuse more

Per K-step a block loads BM·BK + BK·BN elements and does 2·BM·BN·BK FLOPs.

AItile = 2 · BM · BN · BK(BM + BN) · BK · bytes = 2 · BM · BN(BM + BN) · bytes
BK cancels

the pointBK cancels. Reuse depends on the output tile's size and shape. For a fixed area, square tiles are best: BM+BN is smallest relative to BM·BN when BM = BN.

Tile (BM×BN)dtypeFLOP/byte of input loads into the tile
1×1 (naive)fp320.25
32×32fp328
128×128fp3232
128×128bf1664
128×256bf16~85

These counts exclude output writes, partial tiles, and cross-block cache reuse. They describe the tile's input traffic, not measured HBM traffic. Bigger BK leaves this ratio unchanged but alters SMEM capacity, synchronization frequency, and how a pipeline can be organized.

14 Down to registers

The same trick, one level down

whole matrix C
  └─ block tile  (e.g. 128×128)   ← staged in SMEM
      └─ warp tile  (e.g. 64×32)   ← each warp owns a sub-tile
          └─ thread tile (e.g. 8×8)  ← 64 outputs accumulated in registers

What a thread tile changes

A thread owning an 8×8 patch loads 8 values of A and 8 of B from SMEM per k step — 16 loads — and does 8×8 = 64 FMAs.

4 FMA per SMEM load  vs  0.5 in the simple tiled kernel

Registers become the busy layer and SMEM traffic drops.

Vectorized loads

Load 4 floats (128 bits) per instruction instead of four separate loads. Fewer instructions, same bytes.

Transpose A in SMEM

Store A column-wise so the inner loop reads it with vectorized, conflict-free loads. The stores get scattered and awkward, but they happen once per tile while the reads happen many times.

rule of thumbOptimize the access pattern that happens most often.

The data flow becomes: global loads (possibly cached) → SMEM → registers → repeated FMAs. A well-tuned classic kernel reaches tens of TFLOP/s in fp32 with no Hopper-specific features.

15 Bulk transfer

TMA — a delivery robot for tiles

With ordinary loads, threads compute addresses and move tile pieces into SMEM, spending instructions and registers on movement. The Tensor Memory Accelerator is a dedicated copy engine that does it for them.

1 · host

create a tensor map once: shape, strides, box size, swizzle mode

→

2 · one thread

“copy tile (x,y) into this buffer” — returns immediately

→

3 · TMA

copies asynchronously, handling addresses, bounds, swizzling

→

4 · mbarrier

counts arrived transaction bytes and releases the consumer

Synchronization changes what it counts

An mbarrier for a TMA load tracks expected transaction bytes as well as participating arrivals and a reusable phase. Synchronization now tracks data arrival, which is what asynchronous hardware needs.

Memory “proxies”

TMA and Tensor Cores reach memory through a different path than normal thread loads and stores. If threads write SMEM and then TMA reads it, you need a special fence. The required ordering depends on which agents read and write the data.

16 Matrix instructions

WGMMA and the register budget

Ordinary cores do one scalar FMA per thread per instruction. Tensor Cores do a whole small matrix multiply-accumulate in one operation.

D = A × B + D
accumulate
  • Warp group issues it: 4 warps = 128 threads cooperating.
  • Shape m64nNk16 for bf16, where N can be 8, 16, 24, …, 256.
  • A from registers or SMEM, B must be in SMEM, accumulator D lives in registers spread over the 128 threads.
regs/thread = 64 × N128
N = 64 → 32  ·  N = 256 → 128
remember this

Asynchronous — a lifetime rule

wgmma.fence           // order earlier register writes
wgmma.mma_async × 4   // they run in the background
wgmma.commit_group    // bundle them into a group
wgmma.wait_group 0    // wait before using or reusing

Issue independent work early, and wait before consuming results or reusing storage. A late wait helps only if it still preserves every dependency.

Result

TMA + Tensor Cores with a simple 64×64×64 tiling took throughput from ~32 → ~317 TFLOP/s (also switching fp32 → bf16). Much of chapter 4's hand choreography becomes a few hardware-assisted operations — but you still design the tile shapes, layouts, and synchronization.

17 Bank conflicts

Swizzling — permute the addresses

Shared memory is split into 32 banks, each 4 bytes wide. Consecutive 4-byte words go to consecutive banks.

// float tile[32][32], row-major. Thread t reads column c
address = (t * 32 + c) * 4
bank    = (t * 32 + c) % 32 = c     // same bank for every t!
→ a 32-way conflict

// classic fix: padding
float tile[32][33];
bank = (t * 33 + c) % 32 = (t + c) % 32   // all different
// Hopper's preferred fix: swizzle (wastes nothing)
physical_col = c ^ r        // ^ = bitwise XOR

read column c → c^0, c^1, …, c^31   all different banks
read row r    → 0^r, 1^r, …, 31^r   all different banks
recover       → (c ^ r) ^ r = c     // nothing is lost

// 4×4 toy, col' = c ^ r
logical  row1: b0 b1 b2 b3
physical row1: b1 b0 b3 b2

What hardware does

Swizzling works on 16-byte chunks, not single elements. Modes are 32B, 64B, and 128B.

Who needs to know

TMA writes tiles into SMEM in this layout, and Tensor Core instructions are told the mode so they read it correctly. You choose it once in the tensor map.

Don't over-claim it

It distributes the intended chunk-level pattern across banks. It does not make every possible scalar column access conflict-free — check the instruction's actual access width.

18 Overlap

The producer–consumer pipeline

TMA and Tensor Cores are both fast, but in the basic kernel they take turns. Split SMEM into several slots: a producer fills slots while a consumer computes on already-full ones.

time ──▶
TMA    (producer):  [load 0][load 1][load 2][load 3][load 4][load 5] …
Tensor (consumer):          [comp 0][comp 1][comp 2][comp 3][comp 4] …
                    ↑ both units busy at once · slots reused in a ring: 0,1,2,3,0,1,…
BarrierMeaningWaitsSignals
full[i]“slot i has data”consumerTMA (byte count)
empty[i]“slot i is free”producerconsumer (done reading)

Issuing is not finishing

Signaling empty right after issuing WGMMA could let the producer overwrite a tile the matrix unit is still reading. A simple design waits for all committed groups; a more advanced one tracks which groups still use each slot.

An idealized count: a tile loads in 3 units and computes in 5. Four tiles serially take 4 × (3+5) = 32. With separate buffers and perfect overlap: the first load takes 3, then four computations take 20 — 23 units. The gain comes from overlap; neither stage got faster.

What the sketch leaves out

It omits PTX syntax, barrier initialization, arrival counts, phase tracking, and proxy fences. A ring reuses its barriers, so consumers must distinguish the current reuse from a previous completion. Slots begin logically empty, and the initial protocol must permit their first fill. With multiple consumers, a slot becomes empty only when all relevant readers are finished.

Enough stages can cover part of the latency, but throughput is still limited by the slower stage, resource contention, and the pipeline's initial fill and final drain.

19 Resource limits

Split work to fit the hardware

We want a bigger tile, say 128×256. Could one consumer warp group own it?

128 × 256128 threads = 256 regs/thread
> 255 — the architectural maximum
does not fit
64 × 256128 threads = 128 regs/thread
two groups, each owning a 64×256 half
fits

Spilling is not a workaround

Ordinary compiler-managed values can spill to local memory backed by device memory, which can be expensive. But a fixed WGMMA register operand layout must itself satisfy the instruction's constraints — spilling cannot make an oversized accumulator legal.

Rebalancing with setmaxnreg

The producer barely needs registers (it issues TMA commands); consumers need a lot (accumulators). Hopper lets warp groups hand registers to each other at runtime.

128×40 + 256×232 = 64,512 ≤ 65,536 ✓

the lessonSplit work not only for parallelism, but to fit within hardware resource limits. Separate output ownership removes conflicting accumulator writes — it does not remove coordination over the shared input buffers: the producer must wait for both consumers before overwriting a slot.

20 L2 locality

Even the order you walk C matters

To compute one output tile, an SM needs one row-panel of A and one column-panel of B. Tiles running at the same moment that sit in the same rows or columns of C can share those panels through L2.

ScheduleWhat round 1 touchesPanel footprint
Naive (raster) — a run of consecutive tiles per SM8/8 of A + 6/8 of B64 + 48 = 112 MiB
Block-wise — handed out in 4×2 groups4/8 of A + 4/8 of B32 + 32 = 64 MiB
Hilbert curve — only ever steps to a neighbour3/8 of A + 4/8 of B24 + 32 = 56 MiB
Hilbert curve on a 4×4 grid (visit order):
 0  1 14 15
 3  2 13 12
 4  7  8 11
 5  6  9 10
No jumps back across the matrix at a row's end.

Read it honestly

Each 4096×4096 fp32 matrix is 64 MiB and the H100's L2 is 50 MB. Even the 56 MiB Hilbert footprint exceeds it. Compact tile groups are an opportunity for reuse, not a guarantee that accesses hit.

With a persistent kernel, you assign the tile order. Blocks advance at different rates, so a “wave” is a scheduling model, not a hardware-wide barrier. Same matrix, same arithmetic, same hardware — a different order, more cache hits.

22 Beyond matmul

Not every kernel wants tiles

Vector add — nothing to reuse

C[i] = A[i] + B[i]  →  1/12 FLOP/byte

Reads eight input bytes, writes four. Copying every input into SMEM would add work without creating reuse. Start instead with coalesced accesses, enough parallel work, and no unnecessary transfers.

Transpose — layout dominates

If lanes read neighbouring inputs, their direct output writes are far apart. A SMEM tile lets threads cooperate: read contiguously, synchronize, then read it in a different arrangement for contiguous writes.

Now the column reads inside SMEM may conflict. Padding or swizzling solves a different problem from global coalescing.

Reduction

a b c d e f g h
 a+b c+d e+f g+h
   a..d     e..h
       a..h

A tree exposes parallel work early and less near the root. Changing the tree changes the order of floating-point additions, hence the rounding. Correctness includes a numerical accuracy requirement.

Fusion

20 bytes → 12 bytes

Separate kernels read A and B, write T, read T, write C. A fused kernel keeps the sum in a register and writes only C — and removes a launch.

A requested-traffic model: T may be cached, and fusion can raise register use or constrain scheduling.

Irregular work

Graph traversal and sparse computation follow indices to unrelated addresses: little locality, many dependent loads, uneven work per thread. Adding threads does not guarantee throughput.

Compare the entire operation, including reordering or packing — not just the best inner loop.

23 Discipline

Correctness first, then measurement

Check every output

Include rectangular matrices, sizes smaller than a tile, sizes not divisible by a tile, zeros, and mixed-sign inputs. A kernel that works only on 4096×4096 may have an indexing bug hidden by that convenient shape.

abs(actual − ref) ≤ atol + rtol · abs(ref)

Reject nonfinite output too. A tolerance is part of the numerical contract, not permission to ignore arbitrary error.

What exactly did the timer measure?

A launch returns to the CPU before the GPU finishes, so timing the host call measures nothing. Record CUDA events around repeated launches, wait for the stop event, divide by the repeat count — and warm up outside the timed region.

Report it as kernel timing, not application time. Repeated use of the same arrays keeps data in cache — never silently compare warm-cache and cold-cache results.

0.60 + 0.402 = 0.80  →  1.25×, not 2×
Amdahl

If 40% of application time is in the kernel and 60% elsewhere, making the kernel twice as fast makes the application 1.25× faster. A small kernel speedup may barely move the program.

Ask the profiler a specific question first: “this change should reduce SMEM loads.” A profiler records hardware activity; it does not identify the best algorithm.

For a new kernel: start with correctness, map the work and data, predict a bottleneck, measure. Change one important factor, then check both the answer and the timing again.

The most useful question

Not “how many instructions am I running?” but:

“What hardware is waiting right now, and why?”

  • Are the Tensor Cores waiting on SMEM?
  • Is SMEM waiting on HBM?
  • Are threads waiting at a barrier?
  • Are SMs idle because the last wave is mostly empty?
  • Is data being loaded again that another SM already loaded?

Every wait is a clue.

the kitchenHBM is the warehouse across town, L2 the shared pantry, SMEM the ingredients on your workstation, registers what is in the chef's hands, TMA a robot that keeps bringing the next ingredients, and Tensor Cores the chefs — extremely fast if the ingredients are ready. Never make the chefs wait.

Reading the colours and stamps

Three colours recur with one fixed meaning each: cyan for memory and data movement, amber for arithmetic and its ceilings, pink for waste, stalls, and caveats.

The stamp under each slide declares what kind of claim it makes. Reported throughputs come from the source case study, not from runs of this deck. FP32 and bf16 results are not one controlled comparison. Hardware numbers are labelled examples, especially where H100 SXM and PCIe differ.
